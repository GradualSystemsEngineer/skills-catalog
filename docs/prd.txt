Skills Catalog PRD
Owner: Glenn Weigold. Status: draft. Version 0.1.0.
Skills Catalog
One-sentence value proposition: "We help developers reuse each other's AI-
assistant skills consistently, with little effort, by letting them publish a skill to a
shared catalog that another developer's AI assistant can discover and retrieve
on request."
This is a time-boxed build exercise (~4 hours). It defines what to build and the
product outcomes that matter; every technical choice, language, storage, how
the assistant reaches the catalog, is yours. We care more about your thinking
than about how much you ship.
1. Problem Statement
Current state: Developers each build their own reusable instructions for AI assistants ("skills").
A skill lives locally, on the author's own machine, there's no shared place it exists. When one
developer writes a good one, the only way for another to use it is for the author to hand that
local copy over: send the file, or push it to a repo the other developer then clones.
Pain: Because the skill only exists on the author's machine, every share is a copy made by hand,
high-effort and immediately drifting out of sync. The second developer ends up with a stale
copy, a slightly different version, or writes their own from scratch, so the same skill exists in
several inconsistent forms, none of them a single source of truth.
Impact: Duplicated effort and inconsistent results across developers. A shared skill that should
spread cleanly instead fragments.

5. Use Cases
UC-01: Publish a skill
Actor: Developer 1
Precondition: Developer 1 has a skill (a manifest, optionally with supporting files).
Main flow:
1. Developer 1 publishes the skill to the catalog.
2. The catalog stores it and makes it available to others.
Postcondition: The skill is discoverable and retrievable by another developer.
Exceptions:
Skill is missing a name, description, or body: it's rejected with an explanation; nothing partial is
stored.
UC-02: Discover a skill through an AI assistant
Actor: Developer 2
Precondition: At least one skill has been published.
Main flow:
1. Developer 2 asks their AI assistant, in natural language, whether a skill exists for a need.
2. The assistant searches the catalog and returns matching skills.
Postcondition: Developer 2 knows which relevant skills exist, without contacting the author.
Exceptions:
Nothing matches: the assistant clearly says so.
UC-03: Retrieve a skill through an AI assistant
Actor: Developer 2
Precondition: The target skill has been published.
Main flow:
1. Developer 2 asks their AI assistant to get a named skill.

2. The assistant retrieves the skill from the catalog, complete and unchanged.
Postcondition: Developer 2 has the same skill Developer 1 published, ready to use.
Exceptions:
The skill doesn't exist: the assistant returns a clear "not found."
UC-04: Publish a new version of an existing skill
Actor: Developer 1
Precondition: A skill with that name is already published.
Main flow:
1. Developer 1 publishes an updated skill under the same name.
2. The catalog stores it as a new version and retains the previous one.
Postcondition: The latest version is what others retrieve by default; earlier versions remain
available and the history is visible.
Exceptions:
The update is malformed: it's rejected; the existing version(s) are untouched.
6. Functional Requirements
FR-01: Publish a skill
Story: As Developer 1, I want to publish my skill to the catalog so another developer can reuse it
without me handing over files.
Acceptance Criteria:
A developer can publish a skill (manifest + any supporting files) to the catalog.
A published skill is available to another developer, complete.
A skill missing a name, description, or body is rejected with an explanation; nothing partial is
stored.
Input/Output Example:
FR-02: Discover skills through an AI assistant
Story: As Developer 2, I want to ask my AI assistant what skills exist for a need so I can reuse
one instead of writing my own.
1 Input:  Developer 1 publishes skill "release-note-draft" (manifest + a
template file)
2 Output: Skill is stored in the catalog and available to others;
confirmation returned

Acceptance Criteria:
Through an AI assistant, in natural language, a developer can find published skills that match
a described need.
Each result identifies the skill (at least name and description).
When nothing matches, the assistant clearly says so.
Input/Output Example:
FR-03: Retrieve a skill through an AI assistant
Story: As Developer 2, I want my AI assistant to retrieve a published skill so I get the same one
Developer 1 has, ready to use.
Acceptance Criteria:
Through an AI assistant, a developer can retrieve a named skill.
The retrieved skill is complete and unchanged from what was published (manifest +
supporting files).
Retrieving a skill that doesn't exist returns a clear "not found."
Input/Output Example:
FR-04: Version a skill
Story: As Developer 1, I want publishing an updated skill to create a new version so changes are
tracked and nothing is silently overwritten.
Acceptance Criteria:
Publishing a skill whose name already exists creates a new version; prior versions are
retained.
A developer can see a skill's version history.
Retrieving a skill returns the latest version by default; an earlier version can be retrieved when
asked for.
Input/Output Example:
1 Input:  Developer 2 asks their assistant "is there a skill for writing
release notes?"
2 Output: The assistant returns "release-note-draft" with its description
1 Input:  Developer 2 asks their assistant "get me the release-note-draft
skill"
2 Output: The assistant returns the skill, intact and ready to use
1 Input:  Developer 1 re-publishes "release-note-draft" with an edit
2 Output: A new version is stored; the previous version is still
available; history shows both

9. Assumptions and Constraints
Assumptions:
Developers reach the catalog through an AI assistant as the primary access path; if that isn't
available, the access model changes.
The skill format (manifest + optional supporting files) is sufficient for the skills developers
want to share.
Constraints:
Time-boxed exercise (~4 hours). Scope accordingly, a smaller, coherent, working system
beats a larger broken one.
Self-contained: it should run on a reviewer's machine from a short README.
